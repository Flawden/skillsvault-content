# CRN-M-02 — Барабаны, блоки, полиспасты
# D3 Practice v1
## Причинные модели, конкурирующие гипотезы и различающие данные

---

# Зачем эта практика

D3 проверяет уже не способность описать состояние механизма и не способность выбрать одну удобную формулу. Он проверяет, умеешь ли ты **сохранить несколько конкурирующих объяснений до тех пор, пока evidence действительно не разделит их**.

Рабочий маршрут для каждого кейса:

```text
OBSERVED SIGNATURE
→ SYSTEM / MODE / TIME WINDOW
→ HISTORY / STATE
→ H1 / H2 / H3 / H_data WHEN RELEVANT
→ PREDICTIONS
→ EVIDENCE MATRIX
→ OBSERVABILITY CHECK
→ DISCRIMINATING DATA
→ MODEL UPDATE
→ UNKNOWN REGISTER
→ BOUNDED CONCLUSION
```

D3 Practice не просит выдавать формальный `root cause`, remaining-life number, design proof, acceptance/discard verdict или разрешение на изменение реального ПС.

---

# Формат ответа

Для каждого кейса используй один и тот же каркас.

1. **OBSERVED** — что действительно наблюдалось, без объяснения причины.
2. **SYSTEM / MODE / WINDOW** — какой участок/узел, режим и временное окно рассматриваются.
3. **HYPOTHESES** — минимум две конкурирующие причинные модели; `H_data` добавляй только если качество данных реально способно породить сигнатуру.
4. **PREDICTIONS** — что должна давать каждая гипотеза, если она верна.
5. **DISTINGUISHING DATA** — какое следующее наблюдение разделяет модели.
6. **OBSERVABILITY** — способен ли текущий способ контроля вообще увидеть ожидаемый признак.
7. **UNKNOWN REGISTER** — какие неизвестные нельзя молча заменить нулём или «типичным» значением.
8. **MODEL STATUS** — выбери подходящий статус D3.
9. **BOUNDED CONCLUSION** — что можно утверждать сейчас и чего нельзя.

Карманные guards:

```text
PLAUSIBLE ≠ SUPPORTED ≠ FORMAL ROOT CAUSE
BEST SUPPORTED ≠ CLOSED-WORLD PROOF
NON-DETECTION ≠ FALSIFICATION WITHOUT OBSERVABILITY
H_data ≠ TRASH BIN
NOT MEASURED ≠ ZERO
PREDICTED DIRECTION ≠ IDENTIFIED CAUSAL EFFECT
BEFORE / AFTER ≠ ONE CAUSE PROVEN
SOURCE EXISTS ≠ METHOD APPLICABLE ≠ AUTHORITY GRANTED
```

# Кейс A — Одна локальная сигнатура, три механизма
## Competing hypotheses first

На канате вблизи переходной зоны многослойной навивки обнаружена локализованная сигнатура деградации. Известно только:

- зона действительно совпадает с участком перехода между слоями;
- тот же участок каната также проходит через направляющий блок;
- за последний месяц было несколько тяжёлых циклов;
- точная история положения участка каната по циклам пока не сопоставлена.

### Задача

1. Запиши **OBSERVED** одной фразой без слова «причина».
2. Построй минимум три конкурирующие модели, например из семейств spooling/contact, sheave/route и duty/transient history.
3. Для каждой модели назови хотя бы по два ожидаемых признака.
4. Какой следующий факт лучше всего различит H1 и H2?
5. Какой следующий факт лучше всего различит H1 и H3?
6. Какой model-status допустим до получения этих данных?
7. Сформулируй bounded conclusion, не называя root cause.

### Ловушка

```text
СИГНАТУРА НА CROSSOVER-ЗОНЕ
≠
CROSSOVER УЖЕ ДОКАЗАН КАК ROOT CAUSE
```

# Кейс B — Похожие следы после разных маршрутов
## Same signature does not prove same cause

На двух одинаковых механизмах виден похожий локальный паттерн на канате.

**Механизм B1:** участок регулярно проходит через один и тот же блок, а навивка на барабане визуально стабильна.

**Механизм B2:** маршрут через блок недавно изменён, но именно этот участок каната часто попадает в переходную/перекрёстную зону барабана.

### Задача

1. Почему одинаковая внешняя сигнатура не даёт права объединить оба случая в одну причинную модель?
2. Какие history/state переменные нужно вести отдельно для B1 и B2?
3. Составь краткую evidence matrix минимум для H_sheave и H_spooling.
4. Какие данные были бы **confirmatory**, но слабо различающими?
5. Какие данные действительно могли бы разделить H_sheave и H_spooling?
6. Что должно остаться `UNKNOWN`, если точная rope-section mapping отсутствует?

### Ловушка

```text
SAME SIGNATURE
≠
SAME HISTORY
≠
SAME CAUSE
```

# Кейс C — «Не увидели признак»
## Observability before negative evidence

Для H1 аналитик ожидает локальный признак на участке каната внутри труднодоступной зоны. Проведён обычный визуальный осмотр доступных поверхностей; ожидаемый признак не зафиксирован.

Неизвестно:

- была ли нужная поверхность доступна;
- хватала ли чувствительность метода;
- совпадает ли проверенный участок с нужной rope-section mapping;
- попадает ли осмотр в релевантное временное окно.

Коллега говорит:

> «Признака нет — H1 опровергнута».

### Задача

1. Какие четыре observability-вопроса нужно задать до такой фразы?
2. Что означает `non-detection`, если coverage неизвестно?
3. Как классифицировать этот элемент evidence matrix сейчас: `UNEXPECTED`, `UNKNOWN` или `MODEL INVALIDATED`?
4. Какой осмотр/измерение мог бы превратить отсутствие признака в содержательное negative evidence?
5. Сформулируй bounded conclusion.

### Ловушка

```text
NOT OBSERVED
≠
PROVEN ABSENT
```

# Кейс D — `H_data` как настоящая гипотеза
## Data artifact must also predict something

Monitoring показывает резкий единичный всплеск параметра именно в момент события. Физический осмотр после события не показывает ожидаемой локальной сигнатуры. При этом известно, что:

- часы контроллера и журнала эксплуатации могли иметь рассинхронизацию;
- датчик недавно снимали и устанавливали обратно;
- другие каналы записи доступны.

### Задача

1. Сформулируй физическую H1 и `H_data` так, чтобы обе были фальсифицируемы.
2. Какие наблюдения должен предсказывать именно `H_data`?
3. Что могло бы опровергнуть `H_data`?
4. Почему нельзя использовать `H_data` только как фразу «датчик, наверное, врёт»?
5. Какие независимые каналы/временные привязки стоит проверить первыми?
6. Какой model-status честен сейчас?

### Ловушка

```text
H_data
≠
ОБЪЯСНЕНИЕ ЛЮБОГО НЕУДОБНОГО EVIDENCE
```

# Кейс E — Текущий snapshot хороший, история плохая
## Present state versus accumulated history

Сегодня геометрия и укладка выглядят аккуратно. Однако журнал показывает, что две недели назад механизм несколько смен работал с другой конфигурацией направляющего узла, после чего её вернули обратно. Локальная сигнатура на канате обнаружена только сейчас.

### Задача

1. Раздели `PRESENT STATE` и `ACCUMULATED HISTORY`.
2. Почему текущий хороший snapshot не исключает механизм, действовавший раньше?
3. Какие временные данные нужны для сопоставления rope section с прошлой конфигурацией?
4. Какие гипотезы должны учитывать «память» материала/контакта?
5. Что текущий snapshot может опровергнуть, а что — нет?
6. Сформулируй bounded conclusion.

### Ловушка

```text
СЕЙЧАС НОРМАЛЬНО
≠
ВСЕГДА БЫЛО НОРМАЛЬНО
```

# Кейс F — Переходный режим и старая FBD
## Dynamic state rebuild

Для квазистатического режима ранее была построена корректная FBD выбранной сборки. Теперь анализируется короткий переходный режим, в котором скорость заметно меняется. Ускорение не измерено.

### Задача

1. Что в старой FBD остаётся физически релевантным?
2. Что в **модели баланса** должно быть пересмотрено?
3. Почему `a не измерено` не означает `a = 0`?
4. Какие новые данные могли бы различить H_quasi-static и H_transient-load?
5. Как использовать общую связь `ΣF_ext = m·a_G` без выдумывания crane-specific dynamic factor?
6. Какой model-status допустим без измерения ускорения?
7. Чего D3 не имеет права вычислять из этой общей записи?

### Ловушка

```text
UNMEASURED ACCELERATION
≠
ZERO ACCELERATION
```

# Кейс G — После ремонта стало лучше
## Before/after change bundle

После планового обслуживания нежелательная сигнатура заметно уменьшилась. Во время одного окна работ одновременно:

- заменили блок;
- изменили регулировку направляющего элемента;
- перезаправили канат;
- изменили режим запуска;
- очистили и смазали часть узлов.

Коллега говорит:

> «После замены блока стало лучше — значит блок был причиной».

### Задача

1. Почему это событие является **change bundle**, а не доказательством одной причины?
2. Какие переменные изменились одновременно?
3. Что здесь может быть confounder?
4. При каких дополнительных условиях before/after можно было бы трактовать как более сильный natural-experiment-like evidence?
5. Какой follow-up мог бы отделить вклад блока от остальных изменений?
6. Какой статус допустим для H_block сейчас?

### Ловушка

```text
AFTER CHANGE BECAME BETTER
≠
ONE CHANGED ITEM PROVEN CAUSAL
```

# Кейс H — Направление чувствительности известно
## Sensitivity is not causal identification

По нескольким периодам видно: когда число тяжёлых циклов растёт, локальная сигнатура обычно усиливается. Одновременно в эти же периоды чаще используется другой режим скорости и чаще встречается иная зона навивки.

### Задача

1. Можно ли записать qualitative prediction `heavy-cycle exposure ↑ → response ↑`?
2. Доказывает ли она causal effect сама по себе?
3. Какие переменные могут быть confounder, mediator, proxy или downstream response?
4. Какое различающее наблюдение позволило бы усилить или ослабить H_duty?
5. Почему notation вроде `∂Y/∂x > 0` здесь могла бы создать ложную точность?
6. Сформулируй bounded conclusion без «коэффициента влияния».

### Ловушка

```text
DIRECTIONAL ASSOCIATION
≠
IDENTIFIED CAUSAL EFFECT
```

# Кейс I — Какой источник отвечает на какой вопрос
## Evidence roles are question-specific

Для одного случая доступны:

- inspection record;
- monitoring history;
- OEM manual;
- паспорт;
- заключение специализированной организации по отдельному обследованию.

Нужно ответить на четыре разных вопроса:

1. **Что наблюдалось на конкретном участке вчера?**
2. **Какой режим/история действовали в последние недели?**
3. **Какая конфигурация и какие equipment-specific ограничения предусмотрены изготовителем?**
4. **Можно ли формально подтвердить специальный технический вывод, требующий отдельной компетенции/метода?**

### Задача

1. Для каждого вопроса назови первичную роль evidence.
2. Почему нельзя построить универсальную лестницу «OEM > monitoring > inspection»?
3. Может ли inspection record заменить допустимую конфигурацию из OEM?
4. Может ли OEM manual доказать текущую наблюдаемую сигнатуру?
5. Может ли monitoring history сама по себе стать remaining-life certification?
6. Сформулируй правило выбора evidence.

### Ловушка

```text
СНАЧАЛА ВОПРОС
→ ПОТОМ РОЛЬ EVIDENCE
```

# Кейс J — Стандарт найден, расчёт ещё не разрешён
## Source existence versus formal-method authority

Аналитик нашёл релевантные по названию стандарты/документы про нагрузки, monitoring/history и состояние каната. Он предлагает:

> «Теперь можно посчитать коэффициент динамичности, remaining life и допустимость эксплуатации — стандарты же есть».

При этом отсутствуют:

- полный применимый метод/текст для требуемого вывода;
- часть обязательных исходных данных;
- подтверждение применимости к конкретному ПС;
- подтверждение требуемой компетенции/полномочий.

### Задача

1. Раздели четыре утверждения: `source exists`, `source applicable`, `data sufficient`, `authority/competence present`.
2. Какие из них ещё не доказаны?
3. Что D3 может сделать с публичным source context без перехода к formal proof?
4. Какие выводы должны остаться `SOURCE / OEM / SPECIALIST REQUIRED`?
5. Почему точная цифра в такой ситуации была бы слабее честного bounded conclusion?

### Ловушка

```text
SOURCE EXISTS
≠
FORMAL METHOD UNLOCKED
```

# Кейс K — Похож ли этот случай на natural experiment?
## Historical comparison with conditions

На двух однотипных механизмах наблюдали похожую сигнатуру. На одном из них из-за производственной необходимости независимая команда изменила только один документированный элемент маршрута каната; второй механизм остался без изменения. После этого собирали одинаковые inspection/monitoring данные в сопоставимом режиме.

Но неизвестно, полностью ли совпадали:

- нагрузочный спектр;
- состояние канатов до изменения;
- обслуживание;
- environmental/contact conditions.

### Задача

1. Что делает этот случай **сильнее** обычного multi-change before/after?
2. Почему его всё равно нельзя автоматически назвать контролируемым экспериментом?
3. Какие baseline differences и confounders нужно проверить?
4. Какие результаты после изменения усилили бы H_route?
5. Какие результаты ослабили бы H_route?
6. Когда термин `natural experiment` здесь станет более оправданным, а когда лучше оставить `historical comparative evidence`?

### Ловушка

```text
COMPARISON GROUP EXISTS
≠
ALL CONFOUNDERS CONTROLLED
```

# Кейс L — Полный D3 case file
## Integrated transfer case without a single answer

На одном ПС обнаружена локальная сигнатура на участке каната. Доступны следующие факты:

- участок может попадать в transition/crossover context, но точная cycle-by-cycle mapping неполна;
- три недели назад документированно меняли положение направляющего блока;
- после изменения route появились отдельные эпизоды повышенной вибрации;
- monitoring содержит один сильный всплеск, но синхронизация времени с журналом не подтверждена;
- текущий визуальный snapshot выглядит лучше, чем несколько недель назад;
- точные dynamic loads, fatigue history и remaining life неизвестны;
- OEM/паспорт доступны только частично в этом учебном кейсе.

### Задача

Собери полный D3 case file:

1. **OBSERVED SIGNATURE** — одна нейтральная формулировка.
2. **SYSTEM / MODE / TIME WINDOW** — что именно анализируется.
3. Минимум четыре конкурирующие модели из разных семейств, включая `H_data`, если считаешь её релевантной.
4. Для каждой H — `PREDICTS` и `WOULD BE UNEXPECTED`.
5. Составь evidence matrix `EXPECTED / COMPATIBLE / UNEXPECTED / UNKNOWN` минимум по четырём имеющимся фактам.
6. Укажи, где `non-detection` или current snapshot **не** могут быть negative evidence без observability/history proof.
7. Назови три наиболее ценных следующих действия по сбору данных и объясни, **какие H они различают**.
8. Заполни unknown register минимум из четырёх пунктов.
9. Выдай model-status для наиболее поддержанной текущей модели и минимум одной альтернативы.
10. Сформулируй bounded conclusion максимум в шесть строк.
11. Отдельной строкой напиши, какие выводы остаются запрещены на D3.

### Ловушка

Правильный ответ может закончиться фразой:

```text
PLAUSIBLE — DISTINGUISHING DATA REQUIRED
```

или

```text
SUPPORTED CAUSAL MODEL — BOUNDED
```

если границы evidence действительно названы. Он **не обязан** закончиться формальной root cause.

# Финальный mixed check

Выбери любой один кейс A–K и ответь не более чем в 14 строках:

```text
OBSERVED:
SYSTEM / MODE / WINDOW:
H1:
H2:
H_data (if relevant):
DISTINGUISHING DATA:
OBSERVABILITY:
UNKNOWN:
MODEL STATUS:
BOUNDED CONCLUSION:
```

Если ты не можешь честно выбрать один механизм — это не провал. Провал D3 начинается тогда, когда **неопределённость заменяется уверенным рассказом**.

# Что Practice сознательно не проверяет

Эта практика не является:

- формальным root-cause certification;
- расчётом proof of competence;
- расчётом crane-specific dynamic factor или load combination;
- fatigue-life / remaining-life calculation;
- процедурой discard/acceptance;
- design verification;
- specialist NDT interpretation;
- разрешением на ремонт, rerouting, модернизацию или изменение эксплуатации;
- заменой полного применимого стандарта, паспорта, OEM manual или специализированного заключения.

Следующий этап — **D3 Practice Reasoning v1**. Он покажет корректные траектории рассуждения, допустимые альтернативы и failure modes, но не превратит A–L в единый answer key.
