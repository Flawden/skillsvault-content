# CRN-M-02 — Барабаны, блоки, полиспасты
# D2 Practice Reasoning v1
## Worked reasoning paths для кейсов A–K

---

# Как пользоваться этим документом

Это **не единый answer key**.

D2 проверяет не совпадение с одной фразой, а способность удержать инженерный маршрут:

```text
SYSTEM / MODE
→ ROPE PATH
→ CONTACT NODES
→ LOCAL Ti
→ CHOOSE BODY
→ DRAW FORCES
→ GEOMETRY / SPOOLING STATE
→ MODEL STATUS
→ BOUNDED CONCLUSION
→ SOURCE / OEM IF REQUIRED
```

Сильные ответы могут различаться:

- числом локальных меток `Ti`, если границы сегментов выбраны осмысленно;
- порядком некоторых промежуточных шагов;
- словесным описанием механизма влияния;
- bounded conclusion, когда условие допускает несколько честных уровней неопределённости.

Но сильный ответ **не имеет права** перескочить через guards:

```text
ONE ROPE ≠ PROVEN ONE T EVERYWHERE
BLOCK FBD ≠ ROPE FBD
NO SLIP ≠ UNIVERSAL v_rope = ωr
LAYER RADIUS ≠ UNIVERSAL MOMENT ARM
OBSERVATION ≠ ACCEPT / DISCARD VERDICT
TERM MATCH ≠ APPLICABLE LIMIT
QUASI-STATIC ≠ ACTUAL DYNAMIC LOAD
```

Правильный ответ иногда заканчивается не числом, а одним из статусов:

```text
SIMPLE
QUALITATIVE APPLIED
SOURCE / OEM REQUIRED
NOT YET DEMONSTRATED
```

Это не уход от решения. Это часть решения.

---

# Что оценивается прежде всего

Перед формулой или числом ученик должен показать:

1. **что именно является системой / телом**;
2. **как проходит канат** и где находятся контактные узлы;
3. **какие локальные `Ti` нужны** и почему их равенство доказано или не доказано;
4. **какой FBD строится сейчас**;
5. **какие направления сил, линии действия, радиусы или состояния навивки существенны**;
6. **какая модель допустима** и где её граница;
7. **что реально следует из данных**, а что требует точного источника/OEM.

Совпавшее число при неправильной архитектуре рассуждения не считается сильным ответом.

# Кейс A — Один канат, три локальных состояния
## Segment-tension bookkeeping

### Сильная траектория

Первое наблюдение:

> физическая непрерывность каната не доказывает одинаковое натяжение во всех рассматриваемых состояниях.

Метки `T1`, `T2`, `T3` нужны не потому, что канат «разрезан на три каната», а потому что инженер пока **не имеет права слить разные локальные состояния в одну неизвестную**.

Условный маршрут:

```text
барабан → блок A → блок B → dead end
          T1       T2       T3
```

Здесь разумный bookkeeping может быть таким:

- `T1` — локальное состояние около первого рассматриваемого участка;
- `T2` — состояние после следующего контактного узла;
- `T3` — состояние у конечного закрепления.

Другой ученик может поставить метки немного иначе. Это допустимо, если он ясно говорит, **какой участок / состояние обозначает каждая метка**.

### Что не доказано

Из фразы «это один непрерывный канат» не следует автоматически:

```text
T1 = T2
T2 = T3
T1 = T3
```

Чтобы учебно слить часть или все `Ti`, нужно добавить модельные предпосылки, например:

- пренебрежимо малые потери в рассматриваемых контактах;
- квазистатический режим;
- отсутствие существенного локального эффекта, который требует раздельного состояния;
- достаточно простая контактная модель для конкретного вопроса.

Эти предпосылки должны быть **заявлены**, а не подразумеваться.

### Model status

До дополнительных предпосылок:

```text
QUALITATIVE APPLIED
```

Мы уже умеем строить путь и локальный bookkeeping, но ещё не доказали скалярное равенство натяжений.

### Bounded conclusion

```text
Один физический канат позволяет проследить непрерывный load path,
но данных недостаточно, чтобы объявить T1 = T2 = T3
или назначить численный коэффициент потерь.
```

### Допустимый альтернативный путь

Можно начать с одной общей метки `T?`, а затем при каждом контактном узле спросить: «имею ли я право сохранить ту же величину после этого узла?». Если доказательства нет — метку нужно разделить на локальные `Ti`.

### Типичные провалы

- `A-F1`: «канат один → натяжение везде одинаковое»;
- `A-F2`: придумать коэффициент потерь без источника/модели;
- `A-F3`: считать `Ti` доказательством скачка натяжения ровно в нарисованной границе;
- `A-F4`: не объяснить, что именно обозначает каждая локальная метка.

# Кейс B — Одна точка контакта, две FBD
## Action / reaction discipline

### Сильная траектория

Сначала назвать тело.

## Вариант 1: `FBD: BLOCK`

На блок действуют силы **со стороны каната** в зоне контакта, а также другие внешние силы/реакции, относящиеся к выбранному телу.

Стрелки канатных сил направляются так, как **канат действует на блок**.

## Вариант 2: `FBD: ROPE`

После смены тела надо построить FBD заново.

Теперь в той же зоне контакта рассматривается сила **блока на канат**.

По третьему закону Ньютона контактная пара:

- равна по величине в идеализированном парном описании взаимодействия;
- противоположна по направлению;
- действует на **разные тела**.

Поэтому нельзя взять стрелку из `BLOCK FBD`, оставить её как есть и перенести в уравнение `ROPE FBD`.

### Правильная дисциплина

```text
СМЕНИЛ BODY
→ ОБНУЛИЛ СТАРЫЕ СТРЕЛКИ
→ ЗАНОВО СПРОСИЛ: КТО ДЕЙСТВУЕТ НА ВЫБРАННОЕ ТЕЛО?
→ ПОСТРОИЛ НОВУЮ FBD
→ ТОЛЬКО ПОТОМ УРАВНЕНИЯ
```

### Model status

Для качественной дисциплины FBD:

```text
SIMPLE
```

если задача только про направление action/reaction и не требует реального контактного распределения.

### Bounded conclusion

```text
Одна физическая контактная зона порождает согласованную пару action/reaction,
но стрелки принадлежат разным FBD и не переносятся между ними без смены знака/смысла.
```

### Типичные провалы

- `B-F1`: смешать силы, действующие на блок, с силами, действующими на канат;
- `B-F2`: считать action/reaction двумя силами на одном теле;
- `B-F3`: менять body после написания уравнения, не перестраивая FBD;
- `B-F4`: обсуждать знак силы без объявления выбранного тела и осей.

# Кейс C — Тот же `T`, другая геометрия
## Reaction direction without scalar-angle shortcut

### Сильная траектория

Условие специально даёт:

```text
T1 = T2 = T
```

Поэтому вопрос не о величинах натяжений, а о **направлениях сил**.

Для каждого положения:

1. выбрать `FBD: BLOCK`;
2. провести локальные касательные к направлению ветвей каната;
3. поставить две силы **каната на блок** вдоль этих направлений;
4. сложить их как векторы качественно;
5. определить, как должна измениться реакция опоры, чтобы выполнить выбранный баланс модели.

В положении 1 две ветви имеют одну геометрию. В положении 2 одна ветвь повернулась. Даже при одинаковом `T` векторная сумма меняется.

Следовательно, утверждение:

> «груз тот же и `T` тот же, значит реакция опоры та же»

не доказано.

### Что именно изменилось

В условии неизменными оставлены величины `T`. Масса не объявлена изменившейся.

Явно изменилось:

```text
НАПРАВЛЕНИЕ ОДНОЙ ИЗ СИЛ
```

а значит может измениться результирующая и реакция.

### Почему не нужна случайная скалярная формула через угол

Без точного определения угла и reference geometry легко подставить не тот угол или неверный знак. D2 достаточно векторного вывода.

### Model status

```text
QUALITATIVE APPLIED
```

### Bounded conclusion

```text
При одинаковых величинах T изменение направления ветви может изменить
векторную сумму сил на блок и реакцию опоры.
По одному эскизу нельзя назначить допустимый угол или допустимую нагрузку подшипника.
```

### Типичные провалы

- `C-F1`: «T одинаковое → reaction одинаковая»;
- `C-F2`: использовать формулу через неописанный угол;
- `C-F3`: перейти от качественной реакции к допустимой нагрузке опоры;
- `C-F4`: рисовать силы блока на канат внутри `BLOCK FBD`.

# Кейс D — Окружная кинематика барабана
## `r_k` and a deliberately simple model

### Сильная траектория

Здесь условие специально создаёт простой кинематический случай:

- окружное движение поверхности;
- локально почти окружной контакт;
- существенной осевой/винтовой составляющей нет;
- проскальзыванием пренебрегаем.

`r_k` — кинематический радиус для рассматриваемого окружного движения.

Для поверхности барабана:

```text
v_circ = ω · r_k
       = 2,0 · 0,25
       = 0,50 м/с
```

Это **окружная скорость поверхности**.

При перечисленных предпосылках её можно использовать как учебное приближение скорости каната вдоль рассматриваемого почти окружного контакта.

### Что ломается при переходах

Если канат начинает заметно двигаться по винтовой траектории, переходить между витками или слоями, нужно заново проверить:

- фактическое направление траектории;
- наличие осевой компоненты;
- применимость выбранного `r_k` к нужной величине;
- условие no-slip;
- геометрическое описание контакта.

### Два статуса

Для специально заданной учебной задачи:

```text
SIMPLE
```

Для вопроса «какова допустимая скорость реального механизма?» без применимой документации:

```text
SOURCE / OEM REQUIRED
```

### Bounded conclusion

```text
0,50 м/с — результат учебной окружной кинематики.
Он не является паспортной, допускаемой или безопасной скоростью конкретного механизма.
```

### Типичные провалы

- `D-F1`: назвать `0,50 м/с` допустимой скоростью;
- `D-F2`: забыть, что получена именно `v_circ`;
- `D-F3`: переносить формулу на винтовую укладку без геометрической проверки;
- `D-F4`: смешать `r_k` с плечом момента `r_m`.

# Кейс E — `NO SLIP`, но укладка винтовая
## Helical-spooling kinematic trap

### Сильная траектория

Фраза `no slip` говорит о локальном кинематическом условии контакта. Она **не доказывает**, что пространственная траектория каната совпадает с окружностью барабана.

Если за оборот есть заметное осевое продвижение, путь каната имеет дополнительную геометрическую составляющую.

Поэтому нужно разделить:

```text
окружную скорость точки поверхности барабана
```

и

```text
скорость каната вдоль его фактической траектории
```

Для точной связи потребуется дополнительное геометрическое описание — например, направление/шаг фактической траектории и согласованная кинематическая модель контакта.

D2 не обязан придумывать эту формулу, чтобы сделать корректный вывод.

### Model status

```text
QUALITATIVE APPLIED
```

Точная скалярная связь:

```text
NOT YET DEMONSTRATED
```

### Bounded conclusion

```text
No-slip ограничивает относительное движение в контакте,
но сам по себе не превращает винтовую траекторию каната в окружную.
Универсальное v_rope = ωr не доказано.
```

### Допустимый альтернативный путь

Можно описать скорость через компоненты или касательное направление траектории, не выводя формулу. Ключевое — не объявить окружную компоненту полной скоростью каната без доказательства.

### Типичные провалы

- `E-F1`: `no slip → v_rope = ωr` без проверки траектории;
- `E-F2`: игнорировать осевое продвижение;
- `E-F3`: изобретать pitch/helix formula, которой нет в исходных данных;
- `E-F4`: выдавать качественную модель за численный design criterion.

# Кейс F — Радиус слоя и плечо момента
## `r_k` versus `r_m`

### Положение 1 — доказанная простая касательная модель

Дано:

```text
T = 12 условных единиц силы
r_m = 0,30 условных единиц длины
```

Сила действует касательно, а `r_m` уже объявлен перпендикулярным плечом относительно оси.

Поэтому:

```text
M = T · r_m
  = 12 · 0,30
  = 3,6
```

условных единиц момента.

Здесь используется **`r_m`**, потому что вопрос про момент относительно оси.

Model status:

```text
SIMPLE
```

### Положение 2 — видимый радиус есть, плечо не доказано

Известно только, что видимый радиус текущего слоя равен `0,30`, а линия действия силы отклонена.

Этого недостаточно, чтобы написать тот же момент.

Для момента нужно знать:

```text
перпендикулярное расстояние от оси до линии действия силы
```

или эквивалентную векторную геометрию.

Следовательно:

```text
r_layer = 0,30
≠ автоматически
r_m = 0,30
```

Model status:

```text
QUALITATIVE APPLIED
```

а численный момент:

```text
NOT YET DEMONSTRATED
```

### Bounded conclusion

`r_k` и `r_m` могут численно совпасть в специальной простой геометрии, но это не делает их одной физической величиной по определению.

### Типичные провалы

- `F-F1`: использовать `r_k` только потому, что «это радиус»;
- `F-F2`: принять видимый радиус слоя за плечо момента;
- `F-F3`: сохранить `M=3,6` после изменения линии действия;
- `F-F4`: использовать учебный момент как sizing/strength result.

# Кейс G — Сначала состояние навивки, потом вердикт
## Spooling-state recognition

Главная архитектура:

```text
НАБЛЮДЕНИЕ
→ СОСТОЯНИЕ
→ ВОЗМОЖНЫЙ МЕХАНИЗМ ВЛИЯНИЯ
→ ЧТО НУЖНО ПРОВЕРИТЬ
→ ТОЛЬКО ПОТОМ VERDICT ПО ПРИМЕНИМОЙ ПРОЦЕДУРЕ
```

## G1 — соседние витки в одном слое

Наблюдение можно описать как однослойное соседнее расположение витков без видимого перехода.

Могут иметь значение:

- взаимное положение соседних витков;
- локальный контакт;
- состояние каната и канавки;
- фактическая геометрия укладки.

Но из одной визуальной фразы нельзя вывести `ACCEPT`, `DISCARD` или `REPAIR`.

## G2 — переход на следующий слой

Это transition / layer-change state.

Инженерно важно заметить изменение контактной геометрии и опирания каната. Возможный механизм влияния можно обсуждать качественно, но численные критерии и verdict требуют применимой процедуры.

## G3 — crossover-зона

Наблюдение: участок находится в crossover state многослойной навивки.

Корректный вывод D2:

- контактная история отличается от обычного участка;
- зона заслуживает отдельного внимания в применимой inspection logic;
- само слово `crossover` **не является** браковочным критерием.

## G4 — боковое слежение / контакт

Можно зафиксировать side-tracking/contact observation.

Не доказаны:

- точная причина;
- допустимость геометрии;
- состояние каната;
- необходимость ремонта;
- пригодность механизма к эксплуатации.

### Model status

Для описания состояния и возможного механизма:

```text
QUALITATIVE APPLIED
```

Для реального accept/discard/repair verdict:

```text
SOURCE / OEM REQUIRED
```

### Допустимые разные ответы

Разные ученики могут назвать механизмы влияния разными словами. Это нормально, если они:

1. не выдают механизм за установленную причину;
2. не выдают наблюдение за verdict;
3. явно называют, что нужно проверить дальше.

### Типичные провалы

- `G-F1`: `crossover = браковка`;
- `G-F2`: `видимого повреждения нет = всё допустимо`;
- `G-F3`: назначить численный критерий без источника;
- `G-F4`: перепутать наблюдение, диагноз и разрешение на эксплуатацию.

# Кейс H — Маршрут изменили, груз тот же
## Load-path redistribution

### Сильная траектория

После изменения положения направляющего блока нельзя «сохранить старое решение и поправить картинку».

Нужно заново пройти D2-route:

```text
ROPE PATH
→ CONTACT NODES
→ LOCAL Ti assumptions
→ BODY
→ FBD
→ FORCE DIRECTIONS
→ REACTION / LOAD-PATH CONCLUSION
```

Если масса груза и учебная величина тягового усилия оставлены как условные константы, их можно сохранить **только как данность сравнения**.

Но направления ветвей и силы на блок/опору нужно перечитать из новой геометрии.

Поэтому старая реакция опоры не сохраняется автоматически.

### Что нужно перестроить

Минимум:

- FBD изменённого блока;
- FBD/реакцию его опоры, если это предмет вопроса;
- любые downstream FBD, для которых изменились направления или контактные узлы.

### Почему идеальная кратность не спасает

Одинаковая кратность может описывать один аспект идеальной кинематики/силового выигрыша, но не доказывает одинаковые:

- направления ветвей;
- реакции опор;
- контактные состояния;
- моменты;
- спулинг/геометрические условия;
- допустимость реальной конфигурации.

### Model status

Для сравнения влияния геометрии:

```text
QUALITATIVE APPLIED
```

Для физической перестановки блока реального ПС:

```text
SOURCE / OEM REQUIRED
```

### Bounded conclusion

```text
Изменение положения блока может перераспределить load path даже при том же грузе
и той же идеальной кратности. Реальную перестановку нельзя разрешить по учебному эскизу.
```

### Типичные провалы

- `H-F1`: «груз тот же → reaction та же»;
- `H-F2`: не перестраивать FBD после изменения геометрии;
- `H-F3`: считать одинаковый `n` доказательством эквивалентности схем;
- `H-F4`: превратить учебное сравнение в field modification authority.

---

# Кейс I — Ускоренный подъём
## Quasi-static stop condition

### Сильная траектория

Старая запись:

```text
R_support→block + F_rope→block + F_other = 0
```

является квазистатической моделью выбранного тела.

После появления существенного ускорения нельзя выдавать её за фактический динамический баланс.

Сами физические силы из FBD не «исчезают». Меняется модель баланса.

Концептуально требуется динамическая постановка типа:

```text
ΣF = m a
```

для выбранного тела/системы и согласованных осей, а при необходимости — более полная динамическая модель.

D2 здесь обязан увидеть **stop condition**, а не придумать коэффициент динамичности.

### Model status

Для фактической динамической нагрузки:

```text
SOURCE / OEM REQUIRED
```

или, если вопрос требует полноценной расчётной динамики вне D2:

```text
ESCALATE BEYOND D2
```

### Bounded conclusion

```text
Квазистатическая FBD всё ещё полезна для идентификации сил,
но её равновесие не является фактической динамической нагрузкой при существенном ускорении.
Численный коэффициент динамичности и максимум нагрузки из условия не следуют.
```

### Типичные провалы

- `I-F1`: оставить `ΣF=0`, потому что «силы те же»;
- `I-F2`: удалить старые силы вместо изменения баланса;
- `I-F3`: назначить случайный dynamic factor;
- `I-F4`: использовать D2 как authority для maximum dynamic load.

---

# Кейс J — «Угол вроде тот же»
## Definition / reference-geometry / source trap

### Сильная траектория

До сравнения измеренного угла с найденным пределом нужно доказать несколько разных соответствий:

```text
1. TERM MATCH
2. DEFINITION MATCH
3. REFERENCE-GEOMETRY MATCH
4. APPLICABILITY MATCH
5. CONFIGURATION MATCH
6. DOCUMENT / EDITION / OEM MATCH
```

Похожий перевод термина закрывает максимум первый пункт — и то не всегда.

Численное сравнение без остальных пунктов методически недействительно.

### Три уровня, которые нельзя смешивать

```text
ТЕРМИН
↓
ОПРЕДЕЛЕНИЕ + REFERENCE GEOMETRY
↓
ПРИМЕНИМЫЙ НОРМАТИВНЫЙ / OEM LIMIT
```

### Model status

```text
SOURCE / OEM REQUIRED
```

### Bounded conclusion

```text
Измерен некоторый геометрический угол, но пока не доказано,
что это именно та величина, для которой найден численный предел.
Сравнение и field verdict преждевременны.
```

### Типичные провалы

- `J-F1`: сравнить числа по похожему названию;
- `J-F2`: игнорировать reference geometry;
- `J-F3`: использовать limit из документа для другой конфигурации;
- `J-F4`: назначить новый «универсальный» предел из найденного примера.

---

# Кейс K — Один успешный подъём и режим эксплуатации
## Duty / classification context

### Сильная траектория

Один успешный подъём описывает только один эпизод. Он не описывает весь service context.

Качественно D2 должен помнить категории вроде:

- число / частота рабочих циклов;
- спектр нагрузок;
- характер перемещений;
- повторяемость режима;
- продолжительность/интенсивность использования;
- другие параметры, которые применимая классификационная система требует для реального решения.

Поэтому два механизма, однажды поднявшие одинаковый груз, могут иметь совершенно разные duty contexts.

### Чего D2 не делает

D2 не назначает самостоятельно реальную classification group по нескольким словам из условия.

Для selection/classification решения нужен:

```text
точный применимый классификационный источник
+ требуемые исходные данные
+ equipment/project context
+ при необходимости OEM/design authority
```

### Model status

Для качественного сравнения service context:

```text
QUALITATIVE APPLIED
```

Для реального selection/classification verdict:

```text
SOURCE / OEM REQUIRED
```

### Bounded conclusion

```text
Одинаковый единичный успешный подъём не доказывает одинаковую пригодность
для разных режимов эксплуатации и не определяет одинаковый выбор механизма.
```

### Типичные провалы

- `K-F1`: свести service context к максимальному разовому грузу;
- `K-F2`: самостоятельно назначить classification group;
- `K-F3`: игнорировать повторяемость и load spectrum;
- `K-F4`: путать качественный duty context с полным проектным расчётом.

# Финальный mixed check — как выглядит сильный ответ

Для любого кейса B–K хорошая короткая запись может выглядеть так:

```text
BODY / MODE:
какое тело и какой режим я рассматриваю.

ROPE PATH:
какой путь каната относится к вопросу.

CONTACT NODES:
где меняется контакт / направление / состояние.

LOCAL Ti:
какие метки нужны; какие равенства доказаны, а какие нет.

FBD:
кто действует на выбранное тело.

GEOMETRY / SPOOLING:
какие направления, line of action, r_k/r_m или состояния важны.

MODEL STATUS:
SIMPLE / QUALITATIVE APPLIED / SOURCE-OEM REQUIRED / NOT YET DEMONSTRATED.

BOUNDED CONCLUSION:
что следует из данных и где я останавливаюсь.
```

Если одна строка честно остаётся `NOT YET DEMONSTRATED`, это лучше скрытого допущения.

# Общая failure taxonomy D2

## Семейство F1 — bookkeeping failures

- один канат автоматически превращается в один `T`;
- локальные `Ti` считаются физическими разрывами каната;
- равенство `Ti` вводится без предпосылок.

## Семейство F2 — FBD failures

- тело не объявлено;
- action/reaction помещены на одну FBD;
- стрелки переносятся после смены тела;
- reaction обсуждается без направлений ветвей.

## Семейство F3 — geometry failures

- `r_k` и `r_m` считаются синонимами;
- visible layer radius автоматически принимается за moment arm;
- окружная скорость объявляется полной скоростью вдоль произвольной траектории;
- геометрия меняется, а старая FBD остаётся.

## Семейство F4 — spooling failures

- состояние навивки сразу превращается в диагноз;
- crossover автоматически становится браком;
- боковой контакт автоматически считается допустимым или недопустимым;
- нет разделения observation → mechanism → verdict.

## Семейство F5 — model-status failures

- `SIMPLE` используется там, где исходные допущения уже нарушены;
- `QUALITATIVE APPLIED` выдаётся за точный численный расчёт;
- `SOURCE/OEM REQUIRED` воспринимается как «ничего нельзя сказать» вместо корректной границы вывода;
- скрытое допущение заменяет `NOT YET DEMONSTRATED`.

## Семейство F6 — authority failures

- найденный похожий термин импортирует чужой numeric limit;
- учебное число становится equipment limit;
- qualitative observation становится accept/discard verdict;
- D2 разрешает перестановку блока или изменение геометрии;
- единичный успешный подъём превращается в selection/classification proof.
