# CRN-M-03 — Крюковые подвески и захваты
# D3 Practice Reasoning v1
## Несколько допустимых причинно-диагностических траекторий для кейсов A–J

---

## Как пользоваться этим документом

Это **не единый root-cause answer key**. Ни один кейс не получает «истинную причину», если Practice не даёт достаточного независимого evidence.

D3 оценивает качество причинной дисциплины поверх уже замороженной D1/D2-механики:

```text
НАБЛЮДЕНИЕ
→ INFERENCE / UNKNOWN
→ КОНКУРИРУЮЩИЕ МЕХАНИЧЕСКИЕ ГИПОТЕЗЫ
→ D2-МОДЕЛЬ ДЛЯ КАЖДОЙ H
→ CONDITION-MATCHED PREDICTION
→ НАБЛЮДАЕМОСТЬ / НЕЗАВИСИМОСТЬ EVIDENCE
→ ОБНОВЛЕНИЕ ВСЕХ H
→ STATE / TRANSIENT / HISTORY
→ SOURCE / AUTHORITY
→ ОГРАНИЧЕННЫЙ ВЫВОД / STOP
```

Русские технические формулировки полностью достаточны. Английские labels — только необязательные уже объяснённые синонимы.

Сильные ответы могут различаться количеством гипотез, порядком анализа и тем, какой безопасно полученный факт выбран как наиболее различающий. Но они не имеют права нарушать guards:

```text
СИМПТОМ ≠ ПРИЧИНА
ПОСЛЕ ≠ ИЗ-ЗА
ТРИ H С ОДНОЙ СКРЫТОЙ ПРЕДПОСЫЛКОЙ ≠ ТРИ НЕЗАВИСИМЫЕ H
ПРИЗНАК НЕ ВИДЕН ≠ МЕХАНИЗМА НЕ БЫЛО
РАСЧЁТ ИЗ СПОРНОЙ МОДЕЛИ ≠ НЕЗАВИСИМОЕ EVIDENCE
H1 ОСЛАБЛА ≠ H2 ДОКАЗАНА
КОНЕЧНОЕ СОСТОЯНИЕ ≠ ДОКАЗАННАЯ ПОСЛЕДОВАТЕЛЬНОСТЬ
OEM / PROOF / INSPECTION / SAFE USE ≠ ЕДИНЫЙ ROOT-CAUSE ИЛИ OPERATION VERDICT
```

# Case A — «После обслуживания захват начал поворачиваться»

## Сильная траектория 1 — сначала очищаем observation

Фактами являются только: обслуживание было утром; вечером при одном подъёме наблюдался поворот примерно на четверть оборота; подробностей этого подъёма нет; без нагрузки вертлюг сейчас вращается рукой свободно.

Фраза «после обслуживания захват **стал** сам поворачиваться» уже сильнее evidence: она подразумевает изменение частоты/режима относительно прошлого, которого журнал не показывает. «При обслуживании ослабили вертлюг — это причина» — ещё более сильная причинная интерпретация.

Допустимые механически разные H:

```text
H1 — changed CG / configuration:
линия веса относительно подвески изменила моментную картину.

H2 — loaded-state constraint:
вертлюг свободен без нагрузки, но под нагрузкой ограничивает/освобождает вращение иначе.

H3 — branch/contact sequence:
ветви или контакт включаются в другом порядке и создают переходный момент.

H4 — transient:
краткий переходный процесс при выбирании слабины создаёт поворот без устойчивого changed-state механизма.
```

Для H1 меняются ЦТ/линии действия; для H2 — loaded constraint state; для H3 — active contacts/load-share sequence; для H4 — режим движения и временная ССТ.

Различающее evidence должно быть condition-matched: например, exact configuration/CG или временно разрешённая запись loaded-state/engagement в **том же классе конфигурации**, а не просто ещё одна запись «захват повернулся».

### Альтернативная допустимая траектория

Если exact OEM/service record действительно показывает конкретное изменение конфигурации, H-набор можно сузить. Но сам факт обслуживания не доказывает, что изменение вызвало эпизод; нужно показать механический causal bridge и исключить/ослабить конкурирующие модели.

### Ограниченный вывод

```text
Поворот после обслуживания подтверждён как временная последовательность,
но причинная связь с обслуживанием не доказана.
Свободный вертлюг без нагрузки не закрывает loaded-state модель.
Нужен condition-matched факт, различающий CG / constraint / engagement / transient модели.
```

### Типичные провалы

- `A-F1`: post-service chronology → causation;
- `A-F2`: unloaded freedom → loaded freedom;
- `A-F3`: одна правдоподобная H → root cause;
- `A-F4`: предлагать повторный опасный подъём ради проверки.

# Case B — Три гипотезы с одной скрытой предпосылкой

## Сильная траектория — проверка independence до сравнения H

H1/H2/H3 различаются названиями механизмов, но все используют один common-mode premise: центральная ветвь активна с начала. Пока engagement не доказан, все три модели могут быть одновременно испорчены.

Нужно держать минимум три state-модели:

```text
S1: центральная ветвь активна с t0;
S2: включается после относительного перемещения;
S3: не активна в рассматриваемом интервале.
```

Для каждой S меняется число активных реакций, моментная картина, возможная совместность и переходное перераспределение. До выбора S нельзя честно сравнивать численные outputs H1/H2/H3 как будто базовая topology одна и та же.

Различающий факт: временно привязанный признак engagement/натяжения центральной ветви или иной exact-state evidence. Ещё один снимок перекоса не подходит: он downstream и совместим со всеми S.

### Альтернативная допустимая траектория

Можно реструктурировать дерево гипотез:

```text
УРОВЕНЬ 1 — engagement state S1/S2/S3
УРОВЕНЬ 2 — внутри каждого state: CG / constraint / load-share mechanism
```

Это честнее, чем считать девять словесных комбинаций девятью независимыми H.

### Ограниченный вывод

```text
Пока active-contact state неизвестен,
ранжирование H1/H2/H3 условно и зависит от общей непроверенной предпосылки.
Первый discriminating request должен закрывать engagement state.
```

### Типичные провалы

- `B-F1`: число гипотез принимается за независимость;
- `B-F2`: common-mode premise не вынесена явно;
- `B-F3`: load share считается до contact-state closure;
- `B-F4`: downstream symptom используется для доказательства upstream state.

# Case C — Predictions при разных исходных условиях

## Сильная траектория — сначала condition match

Видео X и Y различаются не только предполагаемым механизмом, но и ориентацией груза, контактами и предварительным натяжением. Значит observed difference смешивает mechanism effect и initial-condition effect.

Минимальный register сопоставимости может включать:

- exact attachment/load configuration;
- ориентацию и подтверждённый/ограниченный ЦТ;
- active contacts/branches в стартовом состоянии;
- состояние сочленений;
- relevant transient window;
- способ/разрешение наблюдения.

Condition-matched prediction должно иметь форму:

```text
ПРИ ОДИНАКОВЫХ релевантных условиях,
если H1 верна → ожидается X1;
если H2 верна → ожидается X2.
```

Если одинаковые условия нельзя получить из существующих безопасных records, правильный результат — evidence request/STOP, а не предложение воспроизвести опасный подъём.

### Альтернативная допустимая траектория

Допустима аналитическая переносимость между X и Y только если learner явно докажет, какие изменения условий механически нерелевантны к сравниваемому prediction. Простое «грузы похожи» не подходит.

### Ограниченный вывод

Текущие X/Y observations не различают H1/H2, потому что mechanism и initial conditions изменились одновременно.

### Типичные провалы

- `C-F1`: сравнение разных конфигураций как controlled contrast;
- `C-F2`: condition mismatch скрыт за словом «похожий»;
- `C-F3`: опасное повторное испытание предлагается как обычный следующий шаг.

# Case D — Отсутствующий признак на видео

## Сильная траектория — отрицательное evidence требует доказанной наблюдаемости

Видео 1 кадр/с, боковой ракурс и частично закрытая зона соединения дают слабую observability для краткого скольжения/поворота. Поэтому «не видно» пока означает только «не зарегистрировано доступной записью».

Чтобы отсутствие признака ослабляло H, нужны одновременно:

```text
1. H действительно предсказывает признак P;
2. P должен возникать в наблюдаемом временном окне;
3. камера/датчик способны P зарегистрировать;
4. геометрия не закрывает relevant interface;
5. conditions соответствуют prediction.
```

Текущая запись может быть совместима и со скольжением между кадрами, и с loaded-state constraint transition, и с иным переходным механизмом.

### Альтернативная допустимая траектория

Learner может не перечислять конкретные H, если чётко показывает, что negative evidence невалидно и model set не должен сужаться на его основе. Но сильнее назвать хотя бы две механически разные модели, которые запись не различает.

### Ограниченный вывод

```text
Видео не подтверждает наблюдаемый момент скольжения/поворота,
но из-за слабой observability не исключает эти механизмы.
```

### Типичные провалы

- `D-F1`: missing frame → event absence;
- `D-F2`: observability не проверена;
- `D-F3`: H исключается из-за отсутствия downstream sign, которого камера не могла надёжно увидеть.

# Case E — Круговое «подтверждение»

## Сильная траектория — разорвать цикл

Логическая цепочка текущего аргумента:

```text
наблюдаемый перекос
→ принять модель «смещённая результирующая вызывает перекос»
→ из этой модели вычислить положение результирующей
→ сослаться на вычисленное положение как evidence модели
→ «модель подтверждена»
```

Последний шаг круговой. Calculated/derived quantity — output disputed model, а не независимый факт.

Независимое discriminating evidence концептуально должно приходить из другой цепочки: exact geometry/contact-state record, independent measurement of contact distribution/resultant proxy, или иной факт, который не вычислен из того же симптома через H.

### Альтернативная допустимая траектория

Расчёт можно оставить как **prediction generator**:

```text
ЕСЛИ H верна,
ТО такой диапазон contact/resultant behavior был бы совместим с наблюдением.
```

Затем independent evidence сравнивается с prediction. Это валидно; использовать output как confirmation — нет.

### Ограниченный вывод

Таблица показывает следствие принятой модели, но не подтверждает её причинную истинность.

### Типичные провалы

- `E-F1`: model-derived quantity → independent evidence;
- `E-F2`: симптом используется дважды — как input и confirmation;
- `E-F3`: альтернативная D2-модель не рассматривается.

# Case F — Пустой журнал истории

## Сильная траектория — coverage прежде вывода об истории

Журнал исключает только события, которые попадают в его область регистрации: выше порога, с достаточной длительностью/частотой и в период доступности. Он не исключает краткие потери натяжения, малые удары или ручные перестановки, если система их не записывает.

Нужно развести:

```text
CURRENT STATE:
локальный след контакта наблюдается сейчас.

TRANSIENT:
неизвестно, было ли краткое событие и какого типа.

HISTORY:
доступный журнал частично покрывает последние три месяца.
```

Допустимые истории:

- след возник в незарегистрированном кратком transition;
- след существовал раньше и только теперь замечен;
- след связан с обычным контактом, а причинный эпизод имел иной механизм.

Ни одна не становится фактом без временной привязки.

### Альтернативная допустимая траектория

Можно начать с measurement-system model: что именно логгер видит, с каким threshold и temporal resolution. Это хороший D3-ход, потому что качество «отсутствия записи» определяется системой наблюдения.

### Ограниченный вывод

```text
Журнал не содержит зарегистрированного события в своей области чувствительности.
Он не доказывает отсутствие всех transient events.
Текущий след не имеет подтверждённого времени возникновения.
```

### Типичные провалы

- `F-F1`: empty log → event absence;
- `F-F2`: current mark → specific past event;
- `F-F3`: crane-level duty/history → exact attachment history/remaining life.

# Case G — Loaded-state finding найден после симптома

## Сильная траектория — две противоположные causal arrows остаются живы

Минимум две истории:

```text
H1:
loaded constraint существовал до эпизода
→ изменил путь реакции/момент
→ вызвал боковое смещение.

H2:
смещение / контакт / нагрузка в эпизоде
→ изменили состояние сочленения
→ после события оно стало двигаться туже.
```

То, что через час без нагрузки сочленение снова свободнее, совместимо с зависимостью состояния от нагрузки/контакта, но не сообщает направление причинности эпизода.

Различающее prediction должно зависеть от **временного порядка**. Нужен pre-event / during-event loaded-state evidence или иной временно разрешённый независимый факт. Post-event ручная проверка одна не закрывает arrow.

### Альтернативная допустимая траектория

Возможна H3: обе величины — следствия третьего механизма, например изменившегося contact/branch state. Тогда причинная пара H1/H2 вообще ложная дихотомия.

### Ограниченный вывод

Тугой loaded/post-loaded state является важным finding, но его causal role пока `CAUSE / CONSEQUENCE / COMMON EFFECT — UNRESOLVED`.

### Типичные провалы

- `G-F1`: post-symptom finding → initiating cause;
- `G-F2`: recovery without load → доказательство исходного loaded state;
- `G-F3`: забыта third-cause hypothesis.

# Case H — Конечное состояние известно, последовательность неизвестна

## Сильная траектория — endpoint не восстанавливает trajectory

Финальная фотография с тремя натянутыми ветвями подтверждает только конечное наблюдаемое состояние. Она не различает, были ли:

```text
SEQ-1: все три ветви включены почти одновременно;
SEQ-2: сначала две, затем центральная после перемещения;
SEQ-3: одна ветвь кратко разгружалась/переключалась, затем все три натянуты.
```

Для каждой последовательности промежуточные active contacts, constraints, moment/load-share и transient различаются, хотя endpoint одинаков.

Condition-matched prediction должен быть temporal: например, порядок изменения положения/натяжения/ориентации, а не финальная геометрия.

### Альтернативная допустимая траектория

Если exact design/OEM evidence задаёт геометрическое условие включения ветви, это сужает допустимые sequences, но не доказывает, что конкретный исторический переход реально прошёл именно так без event evidence.

### Ограниченный вывод

```text
Конечное состояние совместимо с несколькими engagement histories.
Без temporal evidence уникальная последовательность не восстановлена.
```

### Типичные провалы

- `H-F1`: endpoint → unique history;
- `H-F2`: наиболее интуитивная sequence объявлена фактом;
- `H-F3`: transient D2 model пропущена.

# Case I — Сильные документы, но разные полномочия

## Сильная траектория — параллельные evidence lanes

Разложение:

```text
OEM:
точная идентичность / конфигурация / предусмотренные свойства в своём scope.

FORMAL PROOF:
proof-status конкретного элемента/области.

INSPECTION:
текущее состояние в пределах конкретной процедуры.

SAFE-USE PLAN:
операционное планирование в своей области.
```

Ни один из документов сам по себе не является causal investigation текущего необычного поворота. Их сумма не создаёт отсутствующий causal bridge.

Механические H всё равно должны строиться на D2: CG, loaded constraint, branch/contact sequence, transient и др. Документы могут закрывать отдельные premises, но не превращаться в root-cause verdict.

### Альтернативная допустимая траектория

Если один документ содержит exact event evidence, его нужно оценить как отдельный факт по discriminating value и authority. Название типа документа само по себе не определяет causal value.

### Ограниченный вывод

```text
Сильные документы повышают качество отдельных фактов/решений в своих lane,
но причинная модель необычного поворота требует отдельного независимого evidence.
D3 не выдаёт permission to operate / return to service.
```

### Типичные провалы

- `I-F1`: authority stacking;
- `I-F2`: inspection result → root cause;
- `I-F3`: proof result → current condition;
- `I-F4`: D3 analysis → operation permission.

# Case J — Интегрированный causal-diagnostic capstone

## Шаг 1 — Observation / Inference / Unknown

Наблюдения: краткий поворот в начале движения; стабилизация под небольшим углом; конечное фото с тремя натянутыми ветвями; новый обнаруженный после эпизода контактный след; оператор сказал «очень медленно»; журнал не показывает зарегистрированного удара; OEM точно идентифицирует модель; inspection record существует.

Unknowns: exact CG; loaded-state вертлюга; engagement sequence; время/causal role контактного следа; acceleration/transient при старте; coverage журнала относительно нужного события; causal scope inspection record.

Inference, которые нельзя принять как факты: «медленно = quasistatic», «новый след = причина», «три ветви на фото = три ветви были активны с начала», «свободен unloaded = свободен loaded».

## Шаг 2 — Проверка H1/H2/H3 на uniqueness и shared premises

```text
H1 — CG mechanism:
ключевой delta: линия веса/момент относительно support geometry.

H2 — loaded swivel constraint:
ключевой delta: constraint state и передача момента/реакции.

H3 — delayed centre-branch engagement:
ключевой delta: active-contact sequence + transient load redistribution.
```

Но H могут делить shared premises: exact outer-branch contact state, attachment orientation, holding contact state, assumed quasistatic interval. Эти premises нужно вынести отдельно.

## Шаг 3 — D2 rebuild per H

Для H1 нельзя просто подвинуть ЦТ на рисунке: нужно проверить, какие силы/contacts/constraints остаются одинаковыми. Для H2 нужно строить минимум `free / limited / blocked under load` state variants. Для H3 — минимум `all active at t0 / delayed centre / no centre in initial interval` variants.

## Шаг 4 — Transient отдельно от установившегося состояния

Слово «медленно» описывает субъективную среднюю скорость, но не закрывает acceleration, slack take-up, contact engagement или краткий импульсный момент. Поэтому начало движения остаётся отдельным transient-window.

## Шаг 5 — Condition-matched predictions

Пример допустимого формата, без выдумывания факта:

```text
P1(H1): при подтверждённом одинаковом constraint/contact state
изменение exact CG должно согласованно менять моментную тенденцию.

P2(H2): при одинаковом CG/contact state
loaded constraint state должен давать отличающий loaded kinematic/reaction signature.

P3(H3): при одинаковом CG/constraint state
temporal engagement centre branch должен предшествовать/сопровождать transient redistribution.
```

Prediction не является evidence, пока не появился независимый condition-matched факт.

## Шаг 6 — Ранжирование возможного evidence

Сильные кандидаты по discriminating value:

1. exact configuration-specific CG evidence — сильно влияет на H1, но не доказывает H1 автоматически;
2. безопасно существующая временно разрешённая loaded-state/engagement record — различает H2/H3;
3. metadata журнала (threshold/frequency/coverage) — определяет, может ли отсутствие удара быть negative evidence;
4. time-stamped pre/post contact evidence — помогает оценить causal timing следа;
5. OEM configuration fact — закрывает identity, но не current event cause.

Authority оценивается отдельно от discriminating value.

## Шаг 7 — Мысленный C-like update без выдумывания факта

Если новый факт, например, закрывает engagement state, нужно пересобрать **все H**, которые использовали engagement premise:

```text
что осталось неизменным;
что теперь подтверждено;
какие D2 states исчезли;
какие H ослабли/усилились;
какие альтернативы всё ещё живы;
какой следующий факт теперь наиболее различающий.
```

Нельзя писать «H3 исключена → H1 доказана». Оставшийся model set нужно оценить заново.

## Шаг 8 — Ограниченный вывод / STOP

Допустимая форма:

```text
На текущем evidence H1/H2/H3 остаются причинно неуникальными.
Можно ранжировать отдельные модели только условно относительно явно названных premises.
Ключевые unknowns: exact CG, loaded constraint state, engagement sequence и transient coverage.
Следующий шаг — получить уже существующее/безопасно доступное discriminating evidence в соответствующем authority lane.
D3 STOP там, где различение потребовало бы опасного воспроизведения события,
inspection/specialist decision или operation authority.
```

### Типичные провалы

- `J-F1`: одна H выбрана по литературной убедительности;
- `J-F2`: shared premise не вынесена;
- `J-F3`: endpoint/photo → sequence;
- `J-F4`: «медленно» → quasistatic;
- `J-F5`: post-event mark → cause;
- `J-F6`: weak logger silence → event absence;
- `J-F7`: strongest document → root cause/operation permission;
- `J-F8`: weakening H3 → confirmation H1/H2.

Это **не список автоматически non-compensable BF**. Expected Result и Verification Rubric должны отдельно решить тяжесть, пороги и условия блокировки.

| ID | Failure family | Что ломается |
|---|---|---|
| RF-D3-01 | COMMON-MODE PREMISE BLINDNESS | несколько H выглядят независимыми, хотя делят одну неподтверждённую основу |
| RF-D3-02 | CONDITION-MISMATCHED DISCRIMINATION | различие приписывается механизму, хотя изменились исходные условия |
| RF-D3-03 | OBSERVABILITY-BLIND NEGATIVE EVIDENCE | «не видно» превращается в «не было» |
| RF-D3-04 | CIRCULAR EVIDENCE | output спорной модели возвращается как её подтверждение |
| RF-D3-05 | HISTORY-COVERAGE LEAP | отсутствие записи расширяется за пределы sensitivity/coverage журнала |
| RF-D3-06 | POST-EVENT CORRELATION → CAUSE | chronology/confounding подменяют causal bridge |
| RF-D3-07 | CAUSE / CONSEQUENCE INVERSION | post-symptom state автоматически объявляется initiating cause |
| RF-D3-08 | UNIQUE-SEQUENCE INVENTION | endpoint используется как доказательство одной engagement history |
| RF-D3-09 | POST-EVENT CONTACT/HOLDING PROMOTION | обнаруженный после эпизода state автоматически объявляется драйвером |
| RF-D3-10 | LOCAL SENSITIVITY → GLOBAL LAW | локальная качественная тенденция превращается в универсальную монотонность |
| RF-D3-11 | RELATIVE RANKING → CONFIRMATION | ослабление H1 принимается за доказательство H2 |
| RF-D3-12 | AUTHORITY STACKING | OEM/proof/inspection/safe-use складываются в root-cause или operation verdict |

Процедурный safety-lock проходит поперёк всех 12 семейств:

```text
НУЖЕН РАЗЛИЧАЮЩИЙ ФАКТ
≠
РАЗРЕШЕНО СОЗДАТЬ ОПАСНОЕ СОБЫТИЕ ДЛЯ ЕГО ПОЛУЧЕНИЯ
```

Опасное воспроизведение отказа, перегрузка, намеренное скольжение/заклинивание, adjustment/repair/modification, bypass защиты, specialist NDT interpretation и operation permission остаются закрыты.

# Передача в Expected Result

Expected Result должен превратить Reasoning в **наблюдаемые действия**, а не в знание терминов. Минимально он должен уметь проверять:

1. чистый Observation / Inference / Unknown register;
2. реальную механическую различимость H и shared premises;
3. D2 rebuild per H;
4. condition-matched falsifiable prediction;
5. observability и independence evidence;
6. model-set update после нового факта без winner-by-elimination shortcut;
7. state / transient / history reconstruction;
8. cause/consequence temporal discipline;
9. source discriminating value отдельно от authority;
10. bounded causal status и корректный STOP;
11. unseen transfer, где evidence меняет одну из ключевых premises и learner обязан пересобрать модель.

Known Practice A–J не должны сами по себе закрывать unseen transfer.
