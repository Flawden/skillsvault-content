# CRN-M-01 — D3 Calibration Checkpoint v1

## Решение

D3 успешно прошёл полный цикл:

```text
Architecture
→ Source Gates
→ Lesson
→ Editorial
→ Red Team
→ Practice
→ Practice Reasoning
→ Expected Result
→ Verification
→ Alignment
→ Freshness
→ Freeze
```

Теперь фиксируем, какие элементы становятся стандартом.

---

# 1. Что было одноразовой работой по созданию системы

Эти вещи НЕ нужно заново изобретать для каждого Topic:

## 1.1. Модель D / R / V

- D = глубина материала;
- R = уровень способности учащегося;
- V = сила evidence.

Это системный стандарт.

## 1.2. Evidence semantics

- V0–V5;
- provenance;
- VALID / STALE / REQUIRES_RECHECK / SUPERSEDED / REVOKED.

Это системный стандарт.

## 1.3. Общая философия обучения

- понимание до запоминания;
- причина до термина;
- практика обязательна;
- неизвестность разрешена;
- число без области применения запрещено;
- критерий ≠ причина.

Системный стандарт.

## 1.4. Freeze protocol

```text
source freshness
+
alignment
+
red team
+
artifact integrity
+
review required
→ freeze
```

Системный стандарт.

## 1.5. RU-FIRST

Основная учебная проза — русский язык.

Системный стандарт.

# 2. Что обязательно повторяется для каждого Depth

## 2.1. Competency Contract

Перед авторингом нужно ответить:

> что человек сможет делать после этого уровня, чего не мог раньше?

## 2.2. D(n) / D(n+1) boundary

Без этого уровень начинает залезать в следующий.

## 2.3. Source Audit

Обязателен для:
- нормативных утверждений;
- численных критериев;
- OEM-specific claims;
- сложных современных методов.

## 2.4. Lesson

Нужна причинная последовательность, а не каталог фактов.

## 2.5. Practice

Обязательная.

Не должна сводиться к воспроизведению Lesson.

## 2.6. Expected Result

Поведенческий.

## 2.7. Verification Rubric

Должна проверять компетенцию, а не текст ответа.

## 2.8. Alignment

```text
Competency
→ Lesson
→ Practice
→ Expected
→ Rubric
```

## 2.9. Freeze Gate

Перед заморозкой.

---

# 3. Что НЕ обязательно делать как отдельный этап каждый раз

## 3.1. Отдельный Source-Method Gate для каждой части

Нужен только когда:
- начинается источникно чувствительная область;
- появляется новый стандарт;
- появляются числа;
- появляется specialised method;
- высок риск D3/D4 confusion.

Если новая часть просто развивает уже закрытую механику, отдельный gate не нужен.

## 3.2. Огромный Red Team после каждого маленького блока

Лучше:
- локальные проверки во время authoring;
- полный red team после законченного Depth.

## 3.3. Отдельный ZIP на каждый микроблок

Для эталона это было полезно как инженерный след.

В будущем нормальный production unit может быть:
- source gate;
- цельный depth draft;
- final depth freeze.

Микро-ZIP нужен только для рискованных промежуточных состояний.

---

# 4. Что нельзя сокращать никогда

1. Проверку области применения числа.
2. Различение нормативного требования и manufacturer guidance.
3. Причинную модель.
4. Практику.
5. Expected Result.
6. Verification Rubric.
7. Final Alignment.
8. Source freshness перед freeze.
9. Review Required.
10. Версионирование frozen content.

---

# 5. Что D3 доказал о правильном уровне сложности

D3 — это НЕ:

> больше терминов и больше формул.

D3 =

```text
несколько взаимодействующих механизмов
+
конкурирующие модели
+
неполные данные
+
пространственная / циклическая история
+
различающие измерения
+
ограниченный вывод
```

Это теперь стандарт определения D3 для других Topics.

---

# 6. Что D4 НЕ должен быть

D4 нельзя определить как:

> «ещё больше D3».

Он должен добавить новый класс способности:

```text
выбор и критика методов
+
глубокие модели
+
расчётные допущения
+
чувствительность
+
конфликт источников
+
expert review
+
reference-depth
```

Именно это должно быть следующим архитектурным решением.
